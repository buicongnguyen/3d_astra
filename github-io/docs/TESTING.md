# Testing

## Unit tests
`npm test` runs `node:test` files in `tests/*.test.js`: rules, save and replay, missions, tactics, data checks, palettes, string catalogues. They need no browser and take a few seconds.

Golden gameplay pins (K1): `tests/golden-skirmish.test.js`, `golden-defence.test.js` and `golden-story.test.js`; see "Golden pins and baselines" below.

## Browser suites
Each is `npm run test:<name>` (`tests/<name>.mjs`, Playwright) and runs against a built game:

```sh
npx vite build
npx vite preview --host 127.0.0.1 --port <free port> --strictPort
TEST_URL=http://127.0.0.1:<port>/ npm run test:missions
```

Pick a port nothing else uses. Suites check behaviour at desktop 1440x900, phone portrait 390x844 and phone landscape 844x390 where relevant, including text size (11 px minimum) and touch targets (44 px).

## Writing a suite (tests/lib/harness.mjs)
New browser suites use the shared harness; `browser.mjs`, `hotkeys.mjs` and `language.mjs` are the examples (the other scripts keep their own setup and move over one at a time).

```js
import { launchBrowser, openPage, suite, shot } from "./lib/harness.mjs";
const browser = await launchBrowser();
await suite("my-suite", async () => {
  for (const viewport of ["desktop", "portrait", "landscape"]) {   // 1440x900, 390x844, 844x390
    const { page, errors, tap, goto, ready } = await openPage(browser, viewport);
    await goto();                          // TEST_URL with ?test=1 (goto("firstrun") adds more)
    await ready();                         // models parsed and Start enabled
    await tap("#start");                   // tap on phones, click on desktop
    await shot(page, `my-suite-${viewport}`);   // test-results/<name>.png
    assert.deepEqual(errors, []);          // page errors are collected for you
  }
}, { browser });
```
`openPage` also takes `{width, height, mobile}` for odd sizes and `{deviceScaleFactor, timeout}`, and returns `badResponses`. `suite` prints `PASS name (12.3s)` or `FAIL`, closes the browser and sets the exit code; the CI job collects every script's result and time in its step summary.

Service worker: `DIST_DIR=<build folder> npm run test:offline` (default dist/). It serves its own copy of the build under /3d_astra/ and needs no preview server. The worker is not registered under `?test` unless the URL also has `?sw`.

## Mission bot
`npm run check:missions` (about 90 s) plays all sixteen campaign missions through the command layer (the four Faction Chronicles, three missions each, with `--chronicle all`). Each must stay alive for a passive player, not be won by a generic bot too easily, and be won by the objective bot within its time targets. Run it after any change to `src/story/missions.js` or to rules that affect balance.

## CI
`.github/workflows/pages.yml` pins Ubuntu 24.04, runs the unit tests, builds, runs the browser suites in groups (36 groups; `tests/ci-matrix.test.js` fails when a browser suite in package.json is in none of them) and deploys `dist/` on success. A run takes 15 to 30 minutes; a new push cancels the run before it. Nothing deploys while any group is red.

### Run the CI matrix before pushing: `npm run test:ci-local`
GitHub's runners have no GPU and slow cores: a match draws at a few frames a second, so real-time clocks (wave countdowns, scenes, the match clock) run on while a test is still checking. On a desktop with a graphics card those tests pass, then fail in CI; in November 2026 that cost five red runs in a row. `tests/ci-local.mjs` runs the unit tests, builds (and stops if either fails), serves the build on port 4231 and runs every group from pages.yml (`tests/lib/ci-matrix.mjs` reads them) in 4 lanes, as slowly as CI: `tests/lib/ci-like.mjs` (a `node --import` preload) gives every suite software rendering and slows each page's CPU 20x, including the suites that launch Chrome themselves. About an hour for the whole matrix; `npm run check:defence` is not included.

```sh
npm run test:ci-local                     # unit tests, build, every group, CI-like
npm run test:ci-local -- defence story    # some groups (names from pages.yml)
npm run test:ci-local -- --fast           # full speed, real GPU
npm run test:ci-local -- --no-build --no-unit   # reuse dist/, skip npm test
```
Logs go to `test-results/ci-local/<group>--<suite>.log` while each suite runs (old logs are cleared at the start). A suite still running after `CI_LOCAL_TIMEOUT` minutes (default 30, CI's job limit) is stopped and fails. `CI_LOCAL_PORT`, `CI_LOCAL_LANES` and `SLOW_CPU` change the other defaults. It is calibrated on suite times (layout-f: 133 s a viewport here, 110 s in CI), so it catches tests that race a clock over seconds; a race that needs under 4 frames a second (the frame step is capped at 0.25 s) can still pass here. Run `--fast` too: a check read once right after the start can be too early on a fast machine (the factions emblem is attached a frame or two later), so wait for it with `waitForFunction`. First full run (2026-11-13): offline, language, defence, feel and abilities failed CI-like and were fixed; factions failed at full speed only. Writing tests that hold up: freeze the match clock with `window.__frontier.hold = true` and move it with `step(seconds)`; skip scenes (`skipScene()`) before waiting for what follows them; measure related boxes in one `page.evaluate`; reset a countdown before calling a wave instead of racing it.

A side is a type, sized to the budget (default 1000, or the value of the other side when that is a mix), or a mix of exact counts `[["ranger", 6], ["medic", 2]]`; `factions: [a, b]` follow their side across seats; `watch({ sim, a, b, deaths })` returns a fact per battle (`deaths` lists units as they fell). A gate states the mean of the 10 and how many were won, never one layout: Rangers beat Breakers at 1,000 with a mean of +0.53 and 10 of 10.

Baselines (the integrator records them once after Wave 0, into `docs/aaa/results/round2/baseline/`):
- `npm run check:missions -- --json` prints one object per mission and run (no wall-clock field); `--only` takes a comma list. A run stopped by `--timeout` is a row "did not finish": record and compare on a quiet machine.
- `npm run bench:factions -- --jobs 3` plays in forked workers and prints and saves rows in the one-process order (the JSON is byte-identical); `--rules '<json>'` is passed to the Simulation. `tools/skirmish-bench.mjs` takes the same flags, plus `--json` (without the wall-clock `msPerTick`) and `--cap`.
- `npm run baselines:diff` re-runs the fast baselines (`defence`, `missions-standard`) and compares them; `-- --full` all eight; `-- --only a,b`; `-- --record` writes them; `-- --list` prints each command; `-- --dir <folder>` uses another folder. A baseline not recorded yet is reported, not failed. `chronicles` uses `tools/chronicle-check.mjs --json` (applied by the integrator after Wave 0). The wall-clock cap per run is 600 s here (`--timeout`), not the tools' 240 s, so the finale m12 finishes on a loaded machine and every row is a played result.
- `npm run ci:build-job` runs what the CI build job runs (unit tests, `check:defence`, build), for the 2-core timing: `cmd //c "start /affinity 0x3 /wait /b npm run ci:build-job"`.

Render budget (`tests/render-budget.mjs`): a scenario may now be data (`spawn`, `boss: "<type>"`, `variant`, `status`, `rules`; the file's header lists them), every type it puts on screen is loaded first, and asserts check that nothing draws as the stand-in airframe and that no entity is left undrawn for want of a model (`unloaded` in the summary). A new scenario's limit is a new line `Object.assign(limits, { "<name>": <n> });` under the `limits` line. `SOFTWARE_RENDER=1` draws with SwiftShader for screenshots that compare bit for bit (the GPU path differs by 1 in a few pixels from run to run).
